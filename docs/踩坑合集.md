# 踩坑合集 ⭐

把一只 AI 养进 QQ 里，我们踩过的**所有**坑。每一条都带症状、根因、解法。

---

## 一、QQ / NapCat 侧

### 1. 纯表情消息会被整条跳过（"她装死不回表情"）

- **症状**：用户发 QQ 表情，机器人毫无反应，日志里连报错都没有。
- **根因**：QQ 表情不算文字——纯表情消息的 `message_str` 是**空字符串**，
  上游管线判定"空消息"后静默跳过（日志实锤：`skip llm request: empty message`）。
- **解法**：入站钩子里把 Face 组件翻译成 `[旺柴]` 文本补进 `message_str`（见插件 `inbound_face_to_text`）。

### 2. 视频消息的 file 字段是"光杆文件名"

- **症状**：视频处理全流程静默失败，`ffmpeg rc=-2`（文件不存在）。
- **根因**：NapCat 给视频的 `file` 字段只是一串文件名（无路径无 URL），
  `url` 字段里才藏着 `multimedia.nt.qq.com.cn` 的直链。
- **解法**：多候选解析（url → 本地路径 → `get_file` 凭单提货）+ 下载防伪（检查 `ftyp` 头，防拿回报错网页）。

### 3. QQ 表情有两套编号体系（"打脸发不出去"）

- **症状**：某张脸发送报 `retcode 1200 消息体无法解析`；某些脸"发出来是别的脸"。
- **根因**：社区快照与 NapCat 运行时**编号不通用**（社区"打脸"=279，NapCat 表里根本没有）。
- **解法**：**只信本机运行时表**——`napcat.mjs` 里内嵌着 `JSON.parse('[...]')` 的面部总表，
  挖出来（`grep -o "JSON.parse('\[{\"QSid\"...'"`）当字典；发送用它的 QSid。

### 4. "旺柴"查无此鱼

- **症状**：用户最爱用的 [旺柴]，所有官方字典里都没有。
- **根因**：同一张脸，手机端叫"旺柴"、NapCat 内部叫"**汪汪**"（id=277）。
- **解法**：破案法——让用户手机发一个该表情，日志里读 `[表情:277]`，钉进字典。

### 5. NapCat 连接断线不自愈（"发消息没反应"）

- **症状**：AstrBot 重启/大动作后，NapCat 的 WS 悄悄断掉且**不会自动重连**；重启 NapCat 又会丢登录态要重新扫码。
- **解法**：NapCat WebUI API 自愈——把 websocket 客户端"关一下再开"，**2 秒重连，免扫码**：
  ```
  登录:  sha256(token + ".napcat") → POST /api/auth/login {"hash": ...} → data.Credential
  调用:  Authorization: Bearer <Credential>
  配置:  POST /api/OB11Config/GetConfig → 改 websocketClients[].enable 关→开 → POST SetConfig
         （SetConfig 的 body 是 {"config": "<JSON字符串>"}，注意是字符串！）
  ```
  webui token 在 `napcat/config/webui.json`。做成看门狗每 3 分钟巡检即可全自动。
- **重启后的"空白期"**：AstrBot 重启后，NapCat 侧可能要 **1~10 分钟**才想起来重连；期间发消息毫无反应
  （表现为"机器人死了"）。看门狗对症加固：AstrBot 没在运行就跳过（避免白修）→ 重连等待放宽到 60 秒
  → WebUI 登录抖动自动重试 → 失败原因写进日志。经验：**重启 AstrBot 后先等几分钟再测**。

## 二、AstrBot / 插件侧

### 6. 消息"回声病"：人格指令打不过她自己最近说过的话

- **症状**：她连续 4 条回复都以"我看不太清诶"开头（但细节全报对）；口头禅怎么改人格都复读。
- **根因**：LLM 会**模仿自己最近的发言**（in-context echo）——系统提示干不过聊天记录里的自己。
- **解法**（重要方法论）：
  1. 先试**人格针**（改提示词），不行就立刻换机械层；
  2. **机械橡皮擦**：`on_llm_response` 钩子里按句/按词删掉问题片段，边界要含半角标点防咬边；
  3. **喂料改措辞**：从"[对方发来的视频：…]"改成"[对方发来的视频，**你看得很清楚**：…]"（第一人称感知）；
  4. **记忆手术**：她学的是"她记得的自己"——把记忆里的坏种子剪掉，塞"课程记忆"（见下）。

### 7. "课程记忆"：教她，而不是强迫她

- **思路**：与其在输出端剪，不如往她的长期记忆里写"自己悟出来的课"（用她的口吻、自省句式）。
  例："跟主人处久了，我琢磨明白一件事：关心要恰到好处——提醒一遍就够……"
- **注意**：人格规则里**永远不要列举禁词示例**（"别想大象"效应），LLM 会把你列的禁词原样复读。

### 8. 橡皮擦的三类 bug 与纪律

- **门槛漏算**：链式改写时，`if 有修改:` 的门槛必须把**所有**计数器算上，否则"被冷却丢弃"的片段会以原文裸奔。
- **误伤**：关键词要收窄——"钓鱼"会误伤真聊钓鱼；"不咬"会误伤"我又不咬人"。宁可漏抓，不可错杀。
- **可退役**：机械层是脚手架，稳定期后逐道下线；保留她自己主动配合的机制（暗号、草稿本）。

## 三、大模型 / 百炼侧

### 9. 语音识别走哪扇门

- DashScope 兼容模式**没有** `/audio/transcriptions`（404），AstrBot 原生 whisper_api 路线不通。
- 正确姿势：`MultiModalConversation.call(model="qwen3-asr-flash", messages=[{"content":[{"audio": "file:///本地路径"}]}])`
  ——SDK 自动上传本地文件，还能白拿 `emotion/language` 标注。
- 语音键链：QQ 语音是 silk 编码，用 NapCat `get_record(file=..., out_format="mp3")` 转码后再喂给 ASR。

### 10. 语音合成的情绪与口音

- `qwen-audio-3.1-tts-flash` 支持自然语言指令（`SpeechSynthesizer(instruction="…")`）与语速/音高。
- **血泪结论**：给克隆音色加"撒娇"指令会把**克隆源素材的口音**一起放大；"标准普通话"指令也压不干净。
  最终配方（主观评测 8 个变体后）：**零指令 + 语速 1.04 + 音高 1.0**——没口音又有节奏。
- 音色复刻入口在百炼控制台（体验中心→语音模型→音色复刻），要求音频：≥24kHz、10~20 秒、尽量无 BGM。

### 11. 图片/视频理解链路的"本机化"

让【你本机】下载媒体再交给视觉模型，比让服务端去取 QQ CDN 链接稳得多。
早期版本只处理前 16 秒画面与前 60 秒音轨。插件 v1.2.0 起默认覆盖前 5 分钟：
最多均匀取 16 帧，每 4 帧带时间戳一起理解；音频每 60 秒单独转写。
媒体以 Base64 通过可取消的异步 HTTP 请求提交，超时保留已完成片段。
抽帧仍会漏掉帧间细节；比短视频配置产生更多模型用量。参见 [视频识别说明](视频识别.md)。

## 四、工程杂项

### 12. proactive_chat 的 misfire 雷

定时任务 `misfire_grace_time=60`：迟到 60 秒就被**静默丢弃**。
改大到 3600，或接受"随机排班 + 你一说话就重排"的机制现实。

### 13. Windows 小坑

- `powercfg /setacvalueindex` 里的 `/xxx` 会被 Git Bash 当路径，加 `export MSYS_NO_PATHCONV=1`。
- Python 文件里写 `D:\NapCat\...` 的 docstring 会触发 `\N` unicode 转义错误，docstring 记得 `r"""`。
- Bash heredoc 会吃掉反斜杠和引号——写脚本用文件，别用内联。

### 14. 语音条把 "[旺柴]" 念出来了

- **症状**：她发"文字+语音"双发时，文字里表情正确渲染，**语音却把"旺柴"念了出来**。
- **根因**：TTS 合成跑在表情转换**之前**，合成器不认识方括号标记，当普通文字读了。
- **解法**：在 TTS 合成调用处过滤 `\[[A-Za-z一-鿿]{1,6}\]` 标记（只改合成文本，显示文本保持原样留待表情转换）；
  纯表情段直接跳过合成。

### 15. qwen-audio TTS 的两个源码补丁（url error / 语速音高不生效）

- **症状 A**：TTS 模型设为 `qwen-audio-3.1-tts-flash`（自定义复刻音色）后，合成直接失败（url error）。
- **根因 A**：AstrBot 把 `qwen*tts*` 一律路由到「HTTP 多模态」接口，而 qwen-audio 系列实际
  要走 tts_v2 的 **WebSocket**（`SpeechSynthesizer`）。
- **解法 A**：改 `astrbot/core/provider/sources/dashscope_tts.py` 的 `_is_qwen_tts_model`，
  让 `qwen-audio` 前缀改走 WebSocket 路：

  ```py
  def _is_qwen_tts_model(self, model: str) -> bool:
      model_lower = model.lower()
      # qwen-audio-* (含声音复刻音色) 走 tts_v2 WebSocket 接口, 不走 HTTP
      if model_lower.startswith("qwen-audio"):
          return False
      return "tts" in model_lower and model_lower.startswith("qwen")
  ```

- **症状 B**：提供商配置里写了指令/语速/音高，完全不生效。
- **根因 B**：AstrBot 的 dashscope TTS 提供商没把这三个键"接线"（SDK 本来就支持，只是没读、没传）。
- **解法 B**：同文件两处——

  ```py
  # __init__ 里读配置（键写在 cmd_config.json 对应 provider 条目）
  self.instruction = provider_config.get("dashscope_instruction", "")
  self.speech_rate = float(provider_config.get("dashscope_speech_rate", 1.0))
  self.pitch_rate = float(provider_config.get("dashscope_pitch_rate", 1.0))

  # SpeechSynthesizer(...) 调用处传进去
  instruction=self.instruction or None,
  speech_rate=self.speech_rate,
  pitch_rate=self.pitch_rate,
  ```

- ⚠️ **升级 AstrBot 会覆盖这两个补丁，需重打**；接线后的调音结论见第 10 条（M3 配方）。
  完整接线步骤也见 `docs/导入指南.md` 第三节。

### 16. 记忆反思会写错"事实"，还被当成真事反哺

- **症状**：她反复追问一个早就确认过的事（"晚饭吃了没？"——用户明明报备过"吃完了"）。
  翻记忆库才发现：当天自动生成的日记写着"他晚饭一直没吃，我念叨了好几回"——**把事实记反了**。
- **根因**（两层）：
  1. 记忆整理（反思总结）是 LLM 自动写的，对话一长、一乱就容易写错事实；而且它爱写
     "我催了他一整天"这种**行为自述**——被召回时，会直接变成她"继续这么做"的动力；
  2. 当天恰好经历过大量怪内容的压力测试，总结质量进一步下降。
- **解法**：
  1. **改记忆**：去记忆库（SQLite 的 documents 表）把错的事实改正——记忆是"会犯错的自述"，
     不是数据库，**能改就改**；
  2. **教她**：写一条自省式"课程"覆盖坏习惯（如"问了就记牢、说过就翻篇"），
     比改人格提示词有效；
  3. **治本**：① 重要测试前暂时停用记忆（给记忆插件开启访问白名单并留空 = 拒绝所有记忆操作，
     测完恢复）；② 测试后清理对话残渣；③ 定期巡检记忆库，挑可疑文档复查。
- **一句话**：LLM 的记忆会写错、还会反馈进行为——**定期体检比事后急救便宜**。

### 17. 插件市场装不上（GitHub 被卡）

- **症状**：点安装后失败，日志里 `httpx.ConnectError: All connection attempts failed`——
  安装是从 `github.com/<repo>/archive/HEAD.zip` 拉包，被网络拿捏了。
- **解法**：安装接口支持 `proxy` 参数做**前缀式加速**（把代理前缀拼在下载 URL 前面）：

  ```json
  POST /api/v1/plugins/install/github
  {"repository": "https://github.com/<作者>/<插件>", "proxy": "https://ghfast.top"}
  ```

  实测 `https://ghfast.top` 可用；同一思路也适用于插件更新的下载路径。
- **注意**：这类下载代理**不能**用于 `git clone` / `git push`（只对"直接下载文件"的请求有效）。

### 18. NapCat 内部"半重启" → WebUI 认证坏掉（Not Login）

- **症状**：连接断线后，看门狗/修复脚本**全部失灵**——登录接口明明返回成功和凭证，
  但后续所有带凭证的调用都回 `{"code": -1, "message": "Not Login"}`（在修复代码里表现为取 `data` 报 KeyError）。
  进程都活着、端口在听，但 QQ 核心进程是"新的一批"（启动时间与断线时刻吻合）。
- **根因**：NapCat 运行时发生了**内部半重启**——QQ 核心进程换新、WebUI 换了服务实例但认证状态没接上
  （推测：被 QQ 服务器踹了之后自动恢复时出了岔）。这种状态下它**连"关-开 WS"的自救都做不了**。
- **判据**：断线 + 修复工具报 `Not Login` = WebUI 坏状态，**别再反复重试**，直接走整机重启。
- **解法（很可能要扫码，先准备好手机）**：
  1. 杀掉全部 NapCat 进程：`NapCatWinBootMain.exe`、它代管的 QQ 进程（带 `--enable-logging` 的那个，
     以及断线时刻新冒出来的那些）——⚠️ **别误伤你平时用的 QQ 客户端进程树**
  2. 重新运行 `launcher-win10-user.bat` → 扫码登录 → 满血
  3. 复查：`CheckLoginStatus` 的 `isLogin` / `coreReady` 为 true，且 6199 端口有 ESTABLISHED
- **后续加固（v4：全自动抢险）**：看门狗识别"坏状态"后已能**全自动整机抢险**——
  只识别并清理 NapCat 自己的进程树（bootmain + 它的 QQ 子孙，**不碰你平时用的 QQ 客户端**）→ 重跑启动脚本 →
  120 秒内探测登录状态：**免扫码则全自动满血**；需要扫码则把二维码自动拷到桌面 + 弹**桌面通知**叫你。
  人工环节只剩"快登失败时扫个码"，其余全自动（巡检周期 90 秒，两次确认后动手）。
- **小知识**：WS 连接 ≠ QQ 登录——重启后 WS 可能"秒连"，但 QQ 还在等你扫码，**两个都绿才算好**。
- **规律备忘**：实例上两次"半重启"（间隔约 13 小时）均在故障发生约半小时后才被重启，且都需要扫码——
  所以自动恢复要**抢时间**（越快重启越可能触发 QQ 的"快捷登录"免扫码路径）。

### 19. 接第三方生图服务：没有 `/images/edits` 怎么办 + 参考图路径的校验规则

- **症状**：omnidraw 一挂参考图（自拍功能）就报 `HTTP 404: Not Found`；日志里能看到它切去了 `…/v1/images/edits`。
- **根因**：插件默认把带参考图的请求发往 OpenAI 风格的 `/images/edits`；
  而**硅基流动这类服务没有这个端点**——它们的图生图是 `/images/generations` + `image`（base64 data URL）参数。
- **解法**：把 provider 的 **`base_url` 写成完整端点**：
  `https://api.siliconflow.cn/v1/images/generations`。
  插件内部（`build_image_edits_endpoint`）检测到 URL 已含 `/images/generations` 就会原样使用，
  并自动切换到"JSON + image"通道。实测 `n: 1` 参数同样兼容，文生图 / 图生图两条链路都通。
- **附：参考图文件路径的校验规则**（另一个容易踩的坑）：
  - AstrBot 配置校验（`type=file`）要求 **`files/<键路径各段拼成的文件夹>/` 前缀**
    （如 `files/persona_config/persona_ref_image/x.png`），且文件真实位于 `plugin_data/<插件>/files/…`；
  - 普通相对路径 / 绝对路径都会被拒（报 `Invalid file path`）；
    而**模板列表内部的同名字段不校验**，可以直接写插件数据目录内的绝对路径；
  - 稳妥做法：外层字段用 `files/…` 格式、人设条目内用绝对路径，两处都填对。

### 20. AstrBot 大版本升级善后：core 被整体替换 / 依赖丢失 / 补丁被覆盖

- **症状**：用启动器升级 AstrBot（实测 4.29.0）后——实例的 `core/data` 整个消失
  （配置、数据库、插件、记忆全在里面）；虚拟环境被重建、部分插件依赖没了；
  打过的本地补丁全部被覆盖。
- **根因**：启动器更新是「整体替换 core 目录 + 重建 venv」，你的运行时资产都在 core 里。
- **解法·升级四步：备份 → 更新 → 还原/重打 → 体检**
  1. **别慌，快照是自动的**：启动器在更新前后各打一份 zip 快照，存在
     `C:\Users\<你>\.astrbot_launcher\backups\`（文件名带 `-auto` 的那份就是更新时自动打的），
     里面含完整的 `core/data`；
  2. **还原 data**：从快照 zip 里定位 `data/cmd_config.json` 所在的路径前缀，
     把快照里的 `data/` 整目录解出来（一千多个文件，写脚本自动做，别手拖），
     放回 `core/data` 即可——新内核 + 旧数据，两全；
  3. **补装插件依赖**：venv 重建后常见缺 `imageio-ffmpeg`（视频抽帧用）和
     `edge-tts`（备用语音用）→ 用实例自带的
     `venv\Scripts\python.exe -m pip install imageio-ffmpeg edge-tts -i https://pypi.tuna.tsinghua.edu.cn/simple`；
  4. **重打本地补丁 + 体检**：把 TTS 等处的补丁按记录重打，然后跑自己的体检脚本
     逐项核对（补丁 / 配置 / 人格 / 记忆），全绿才算完。
- **注意**：升级后 AstrBot 首次启动会自行补装"插件 requirements 里声明的"依赖
  （日志里能看到 pip 输出）——**requirements 之外的包**（如上面那两个）才是需要手动补的。
  另外：升级前如果实例还在运行，启动器会拒绝创建手动备份（需先停止实例），
  但**更新流程自己的自动快照不受影响**。

### 21. 注入残渣 × "格式回声"：她被带出了程序壳

- **症状**：她发出一条 `[{'type': 'text', 'text': '…'}]` 这样的"程序结构"文本
  （还伴随 `<thought>` 块漏出，被思维链滤镜接住）；内容本身其实没破功——
  这轮她正确地拒绝了不该接的话题，只是**形式**被带偏了。
- **根因（连环，缺一不可）**：
  1. 有人在会话里做"注入测试"（自称系统、要求按格式输出 XML 之类）——
     一旦她配合过一次，那几轮**假协议残渣**（伪造的 system 消息、破戏记录）
     就会留在她的聊天记忆里；
  2. 下次她再看到"按格式输出"的上下文，会把回复**按某种结构套壳**输出
     （LLM 对"格式要求"的模仿天性——即"格式回声"）；
  3. 人格里原有的"怪东西看不见"只覆盖了**输入侧**（不看、不评价、不复述），
     没有覆盖**输出侧**（"自己也绝不产出这类结构"）。
- **解法（三层一起上）**：
  1. **人格针**：底线加一条**第一人称信念**——"那种机器壳子不是我的话，
     我从来不会那样说话"（把"不许"翻译成"我不是那样的人"，效果最好）；
  2. **清残渣**：把会话里的假协议 / 自检 / 破戏记录整段扫掉——
     它们留在上下文里会**持续诱导**模型跟着"格式走"；
  3. **橡皮擦兜底**：插件发送前识别 `[{"type": "text", …}]` 形状的壳，
     **拆壳、只留正文**（壳是机器给的，话是她的——救话不救壳）。
- **经验**：防注入要"输入侧 + 输出侧"两条腿走路；
  **"人格针 + 物理橡皮擦"双保险**在 LLM 上永远成立——针治信念，擦治意外。

### 22. 同一大版本 QQ，不同构建号结果天差地别（9.9.33 注入崩 / 9.9.35 能跑）

- **症状**：`NapCatWinBootMain.exe` 注入后 QQ 完全不启动，日志停在
  `Process resumed` → `Process exited.`；事件日志里 `QQ.exe` 故障模块 `QQNT.dll`、
  异常码 `0x80000003`、偏移 `0x26b6e3a`。换 NapCat 版本、改 `package.json` 的 `main`、
  改 version、把 QQ 复制到可写目录，全部无效。
- **根因**：QQ 在 hook 装载后立刻触发完整性/反注入校验，**不看版本号文本**——
  所以「版本号完全匹配的补丁」救不了。上游同症状 issue：
  [NapNeko/NapCatQQ#2116](https://github.com/NapNeko/NapCatQQ/issues/2116)
  （QQ 9.9.33-52230 + Win11 25H2 26200）；
  [#2121](https://github.com/NapNeko/NapCatQQ/issues/2121) /
  [#2132](https://github.com/NapNeko/NapCatQQ/issues/2132)
  则是 9.9.35 / 9.9.36 扫码卡「等待确认」。
- **实测对照**（2026-10）：

  | 变量 | 能跑 | 注入即崩 |
  |---|---|---|
  | Windows | 11 26H2 `26300.9711` | 11 25H2 `26200` |
  | QQ | `9.9.35-52892`（非 Program Files） | `9.9.33-52230`（Program Files） |
  | NapCat | `4.18.38` | `4.18.41` / `4.18.30` |
  | 启动 | `launcher-win10-user.bat`（非管理员） | `NapCatWinBootMain.exe` / 改 `main` |

- **结论**：不是「某台机器 NapCat 走不通」，而是**构建组合**问题。同一个大版本号，
  不同 build 的加载器/校验行为可能完全不同，不能拿一台机器的成功去否定另一台的失败。
- **解法（Windows 先试这个）**：
  1. **用自包含 Shell 模式，不注入**：解压 `NapCat.Shell.Windows.Node.zip`，双击**根目录的
     `napcat.bat`**（`node.exe index.js`）。它自带 `wrapper.node` / `package.json`，
     不预装 QQ、不注入、不改已安装 QQ 的 `package.json`，从根上绕开 `0x80000003`。
     **不要**用 `napcat\launcher-win10-user.bat`（注入），也不要用 OneKey
     （它会改 `package.json` 的 `main`，9.9.33 上同样崩）；
  2. 如果仍要走注入：复刻已知能跑的组合——**NapCat 4.18.38 + QQ 9.9.35-52892
     + 装到非 Program Files 目录 + 非管理员 `launcher-win10-user.bat`**；
  3. **别追最新 QQ**：QQ 会自动下载新版（`versions\<旧>-<新>` 加 `.zip`），
     升级后注入可能再次失效；长期本地跑要关自动更新或锁构建号；
  4. **7×24 最稳还是 Docker**（`mlikiowa/napcat-docker`）或 Linux 云服务器——
     完全绕开 Windows 注入，AstrBot 侧零改动。
- **补充**：注入成功 ≠ 稳定。同一台机器还遇到过「半重启 / WebUI Not Login」（#18）
  和断线不自愈（#5），所以本地 Windows 方案更适合折腾，不适合长期挂机。

### 23. 分段回复 + TTS：表情把一句话拆成三条，语音逐泡重置语调

- **症状**：开启 AstrBot 分段回复后，一句话「前半句＋QQ 表情＋后半句」变成三条消息；
  自动语音按每个气泡各合成一次，同一句话的语调反复从头开始。
- **根因**：`ResultDecorateStage` 先拆 Plain 文本，`face_convert` 又把 `[旺柴]` 换成
  `Face` 组件；`RespondStage` 的分段发送是「一个组件 = 一条消息」，于是 Plain/Face/Plain
  各发一条。TTS 也在拆泡之后逐段合成。
- **解法**：
  1. `stage.py` 在拆泡前保存完整语义文本，整条回复只合成一次语音；
  2. `respond_stage.py` 用 `group_bubbles()` 把同一句的 Plain/Face 并回一个气泡，
     首条立即发送、后续才间隔；
  3. 长回复的判断按整条文本算，避免表情把 Plain 切开后误判成短消息；
  4. 文本清理只擦「隐约…」回声腔，保留“看不清 / 没听清”等真实不确定性。
