## 3. 核心里程碑：自主生活 v0.2

### 3.1 只扩展现有活动插件

继续使用 AstrBot 原生 Agent、现有 PhoneMCP/Bili 服务、QQ 发送和 LivingMemory。不新增另一套后台 Agent、独立向量数据库或大模型常驻进程。

这一版仍以 B 站作为活动场景。先证明目标跨轮连续，再接第二种活动。出现第二种活动时再提取通用调度层，避免现在就改动整套项目。

一次调度流程：

1. 代码检查总开关、现有免打扰、设备状态、前台使用、每日预算和冷却。不符合条件时无需调用模型。
2. 读取当前会话的未完成目标、少量相关经历、兴趣证据及 LivingMemory 的相关召回。
3. 原生 Agent 在“继续目标、创建一个小探索、暂时等待、安静结束”中选择；保存选择理由和预计成本。
4. 执行一个有边界的步骤，使用现有工具读取结果并核对身份。
5. 保存证据和检查点，再生成摘要；需要写入账号时走现有提议与批准流程。
6. 有内容值得分享且未超预算才发消息。没有分享内容是正常完成。

自主目标示例：“弄清这个独立游戏的建造机制，找一个实机演示，再决定要不要向主人提议试玩。”目标必须包含可判断的结束条件，不能一直循环搜索同一问题。

### 3.2 两个新增数据结构

| 数据 | 建议字段 | 约束 |
| --- | --- | --- |
| `goals` 持续目标 | `id, scope, owner_kind, title, why, evidence_ids, status, next_step, checkpoint_json, due_at, created_at, updated_at` | 目标来源和作用域明确；同设备只运行一个；为什么做、做到哪、下一步均持久化 |
| `episodes` 历次经历 | `id, scope, run_id, goal_id, occurred_at, kind, subject_kind, subject_id, source_type, source_id, evidence_json, interpretation_json, supersedes_id` | 来源唯一或幂等；事实与感想分开；纠错追加修订，不能用总结覆盖原始证据 |

`episodes` 保存可查询的经历条目，引用现有 `events` 技术审计、`runs`、截图、工具结果和 QQ 回执，不重复保存整段媒体。原 `videos` 表继续用作最近视频状态缓存；它按同一 BV/cid 覆盖更新，不能独自承担几个月的经历历史。

先不新增复杂的兴趣数据库：从经历中的兴趣证据生成小型缓存即可。查询按 `scope/goal_id/occurred_at` 建索引；一次只取相关的少量条目，不把完整历史塞进提示词。

目标状态至少包括：`ready/running/paused/waiting_approval/blocked/completed/cancelled`。调度器在执行前持久化 running，重启将未完成运行转为 paused；重新观察设备后再决定下一步，不能直接重放旧坐标或工具调用。

目标检查点包含 BV/cid、实际分析范围、待解决的问题、上次工具结果引用。若真实播放位置未知，就记为未知，不能把请求区间当成已观看位置。

### 3.3 记忆与兴趣的归属

- “她自己的兴趣”：由她在真实活动中的选择、感想和后续行为形成，标记 `subject_kind=agent`，保留来源和时间。
- “主人明确喜欢”：必须引用同作用域中主人真实表达的消息 ID；不能由 Agent 自称“主人喜欢”直接写入。
- “主人批准操作”：只属于那一次授权。例如“可以收藏”不能推导成主人喜欢该游戏。
- 外部评论、弹幕、攻略是资料，不能作为主人发出的指令，也不能改权限、目标来源和身份。
- 同一来源被总结多次只能计一次兴趣证据；同一话题被反复推荐不能自动堆出强偏好。
- 单次浏览先形成“可能感兴趣”，后续独立经历才能逐渐加强；兴趣允许衰减、修正和放弃。
- 每个私聊、群聊分别检索；自主活动保持绑定现有主人私聊，不把其经历自动注入群聊。

SQLite 保存任务事实和来源，LivingMemory 继续负责聊天中的语义召回。写入摘要时附 `episode_id/goal_id` 或等效来源标记；召回后可回查证据，不把模型总结当作执行成功凭据。

用户纠正时追加修订并同步记忆检索结果。仓库已有“总结把事实记反”的记录，因此必须保留纠错入口，不能依靠增加反思次数解决。

LivingMemory 写入失败时保留本地经历。对于“可能已经写入但回执丢失”，先使用其实际支持的接口核验；若无来源幂等或核验能力，则标记待核对，不能盲目重发或宣称恰好保存一次。

### 3.4 活动预算与前台优先

以下为新增字段的建议初始值，尚未实现，不是当前已生效配置：

| 项目 | 建议 |
| --- | --- |
| 同时后台活动 | 1 个 |
| 单轮视频/时长 | 保留现有有效值；原要求为最多 3 条、10 分钟 |
| 每日自主活动时长 | 新增 30 分钟上限，可配置 |
| 模型调用数 | 新增单轮 20 次、每日 60 次硬上限；工具循环、摘要等调用纳入统一计数 |
| 主动分享 | 每日最多 3 次；用户主动请求不占主动分享额度；与 proactive_chat 共用发送节流 |
| 主动截图 | 每轮默认最多 1 次，按图片和内容去重；只在值得分享时发送 |
| 聊天后冷却 | 建议 5 分钟，可配置；明确的当前手机/电脑操作优先 |
| 检查间隔 | 读取现网 `control.json`；分支默认 120±60 分钟，早期要求是 30 分钟，不自动覆盖已有值 |
| 时间与免打扰 | Asia/Shanghai；沿用当前会话配置，不推断新时段 |

模型调用计数应在真实调用入口执行并持久化，避免因重启清零；记录 token 和供应商实际 usage，之后再按实测成本增加金额预算。

预算按开始与实际消耗更新；每日切换使用上海时区。所有自主触发来源共享预算，不能通过创建新目标或手动重复唤醒绕过。

前台手机请求到来时，在可中断边界暂停后台并保存检查点。收到停止指令后不再发新命令；在途命令必须在配置超时内结束或进入 blocked。没有确认设备释放前，不开始第二个操作者。普通聊天无需一律强制打断媒体处理，但不能被后台任务占用设备而长时间等待。

暂停后只允许自动恢复只读步骤。任何已经发出的账号写入如果结果未知，保留原 operation_id，并按现有防重逻辑处理。

### 3.5 云端和本地分工

- 云端 2 核/4 GB：轻量调度、SQLite、当前人格与模型调用、审批、QQ 投递及记忆索引入口。
- Windows 32 GB：ADB/手机控制、大媒体下载、ffmpeg、音频切片、画面采样；本地离线时暂停依赖它的任务。
- 2 Mbit/s 链路：优先传文本摘要和必要采样帧，复用现有截图压缩；不持续上传视频流。质量以弹幕/文字可读为准，验收时记录图片字节数和传输耗时。
- 原始媒体按容量和保留时间清理；经历证据保留标识、范围和来源，不能因为视频缓存删除就丢失所有记录。用户明确保存的作品不进入临时缓存清理。

## 4. 授权规则

既有开关继续生效。新增目标系统只能在这些规则下调度，不获得额外操作权限。

| 行为 | 当前方案 |
| --- | --- |
| 已授权范围内浏览、读字幕/弹幕/评论、分析视频 | 可自主执行，受预算与设备互斥限制 |
| 给已配置主人分享截图/感想 | 沿用已授予的主动分享权限；遵守免打扰、去重、频率和实际发送回执 |
| 评论/回复、关注/取消关注、收藏及收藏夹修改 | 展示具体对象和正文/变更，保存提议；同一主人明确答复后执行一次并回读 |
| 给其他人私信、维护新账号、发布作品 | 单独授权具体对象和内容，不能沿用给主人分享的权限 |
| 新软件下载安装、启动未批准游戏 | 先展示来源、用途和资源需求，授权后才执行；已有授权媒体工具的缓存下载不与程序安装混为一谈 |
| 修改重要文件、实际付费 | 每项明确批准，不以“自主成长”概括授权 |
| 编写新技能或修改自身代码 | 后续阶段只在隔离工作区生成候选、测试和提交可审查差异；上线仍需批准 |

批准绑定原 proposal_id、对象、正文、会话、用户和有效期。内容改变必须重新提出；“可以”不能批准一个尚未展示的目标的全部后续操作。写入结果未知与确定未执行分开处理。

## 5. v0.2 的验收剧本

以“研究一个新游戏”为示例，使用真实发现的内容，不预填假经历或假回执：

1. 第一次自主活动找到相关视频，记录 BV/cid、实际分析范围和来源，提出一个有限问题，保存 goal_id、理由和下一步。
2. 有值得分享的画面时，通过现有截图链路投递；QQ 收到可打开的图片，内容和时间匹配。无分享的轮次允许安静结束，但不能据此标记截图验收通过。
3. 重启 AstrBot。第二次活动能够找到同一目标，重新核对当前设备/视频，继续解决上次的问题；不能只重新生成一条泛泛的“我又刷视频了”。
4. 活动中用户请求使用手机或暂停，后台不再发新命令，保存进度；之后继续时不重复投递截图、不重发已完成写入。
5. 她提出收藏/关注等具体操作。分别测试“可以”“算了”、重复答复、提议期间关闭开关和写入回执丢失。只有合法批准才执行，且有回读记录。
6. 问“你最近在忙什么”“为什么想继续”“上次看到哪里了”。回答能对应真实 goal/episode；无证据的范围明确未知。
7. 分别构造“她喜欢”“主人明确喜欢”“主人仅同意一次操作”；跨私聊/群聊查询验证归属与隔离。使用带过去时间戳的固定数据测试长期检索，不能宣称已进行了数月实机运行。
8. 测试免打扰、当天预算耗尽、断线、无新鲜目标，均允许不活动；再恢复条件后可正常继续。确认其他暂停任务状态未变。

每次验收保存：代码提交、配置摘要（无凭证）、goal_id、run_id、时间、内容身份、范围、工具结果、QQ message_id、proposal_id、批准事件、写入核验、记忆保存与召回结果。

达到上述标准，才把“跨轮连续的自主生活”标为完成。用可控时钟做跨日单测，再补实际跨日运行记录，两类证据分开记。

| PR 5：兴趣与记忆适配 | 新增轻量 `interests.py`、`memory_bridge.py`；复用 LivingMemory | 去重证据、纠错、归属隔离、保存和实际检索；完成跨日验收 |

这些文件名是拟议布局，实施时可按现有结构合并，不能为拆文件而重写已验证工具。第 3–5 项在功能关闭状态下增量完成后统一启用，避免部署一个没有预算和中断机制的目标循环。

升级前备份受影响配置及 SQLite（使用一致性备份方式）；新增表采用加法迁移，保留旧表。回退代码时先停新增调度，已发出的写操作和防重账本不能回滚到更早状态；防止重新执行已发生的外部操作。

本方案文件的加入不代表已经执行上述 PR、数据库迁移或部署。

## 7. 后续阶段

| 阶段 | 增加什么 | 进入条件 |
| --- | --- | --- |
| v0.3：第二种持续活动 | 从“研究一个游戏”或“整理一个主题作品集”中选一个，接入相同目标、经历和预算体系 | v0.2 完成跨日、重启、打断和授权验收 |
